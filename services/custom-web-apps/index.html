04 / Custom web applications

Custom web applications for practical business workflows.

When a spreadsheet, a generic form, or a collection of disconnected tools no longer supports the way a business works, a custom web application can be a useful next step. I design application interfaces and workflows to make records easier to find, responsibilities clearer, and recurring tasks more manageable, with features driven by the problem rather than by technology alone.

Define the workflow before building screens.

A web application is more than a dashboard. It needs a clear understanding of what information enters the system, where it is stored, what people can do with it, and how a task moves from one stage to the next. Before development, I map out the existing process and ask what causes delays, errors or repeated administrative effort.

For example, a business might want to centralise customer enquiries, maintain a searchable product database, manage internal requests, or build a lightweight application for reviewing records. Each use case has different requirements. We should identify who creates records, who reviews them, who is allowed to make changes and what happens when information is incomplete.

Build around the behaviours people need.

The right interface is usually the one that helps people complete their work without unnecessary steps. I focus on the connections between the screen, the data and the user’s responsibilities. Depending on scope, an application can include:

  • Sign-in and agreed user roles with permissions appropriate to each responsibility.
  • Searchable records, category filters, clear forms, validation and status tracking.
  • Dashboards with metrics based on defined data sources, not placeholder totals.
  • A structured database and an administrative workflow for creating or updating records.
  • Agreed export functions or integrations with existing business systems.
  • Responsive interfaces, accessible controls and testable handling of common errors.

The inputs needed to design the application.

A useful starting point is a description of how work is done today, including sample records, existing forms, tools in use and the roles involved. If an application replaces an existing spreadsheet or platform, a representative sample of the data helps identify relationships between fields and common exceptions. Sensitive information can be removed from examples used for the planning stage.

We also need to agree which tasks should remain outside the application, which data needs to be retained, and where the final system will be hosted. Decisions about user accounts, notifications, integrations and access to business records belong in the scope from the beginning because they affect implementation and maintenance.

An implementation approach that fits the project.

I can work with frontend technologies such as JavaScript, React and Next.js, alongside technologies such as PHP and MySQL where alternatives are appropriate to the application. The stack should follow the requirements, the available hosting, the expected maintenance arrangements and the systems already in place, rather than being chosen just because it is popular.

Development starts with the data model and core workflows, then progresses into usable screens. Testing covers the intended actions, important permissions, validation, handling of incomplete records, and the effect of changes across the application. A phased approach can be useful when stakeholders need to review a working feature before committing to the rest of the scope.

Define reliability, ownership and boundaries.

An application that holds business data needs appropriate backups, account management, monitoring and a maintenance plan suited to the information it handles. Security-conscious development should include a review of access permissions and validation, but specialised independent security assessments, compliance certification and infrastructure operations are separate activities unless they are agreed explicitly.

The portfolio includes examples of front-end product interactions, such as the configurable VELLUNE concept or the SONVIA listening-field experience. These display interaction design and responsive implementation, rather than claiming to be operational business software. A real application would combine those interface principles with the agreed data, backend and operational requirements.
